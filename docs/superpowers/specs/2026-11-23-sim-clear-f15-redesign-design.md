# Sim AI 通关 F15 Redesign 设计规范

> 日期：2026-11-23 · 状态：**未达标，gameplay 改动已回退**（2026-11-24）· 用户目标：**sim 稳定推进到 F15 并赢下若干局**
>
> **实施结果**：按本设计做了约 10 轮 A/B 实验（hunting defer / 楼层锁存 / p_move 门控 / sim 缓和成长曲线 / 成长放大 / 多技能 / 预算放宽 / 拉怪顺序 / 执行层判定统一），经严格 A/B 对照，**多个改动被证明无效或有害**（如 p_move 门控反而使固定 build 卡死 3/4→4/4、成长放大无收益），win_rate 始终 0。用户拍板回退全部未达标 gameplay 改动。
>
> **保留的正确产物**：`is_sim_victory` 纯函数 + 5 契约测试（胜利口径排除超时/看门狗假胜利，已验证正确、不改 sim 行为）。
>
> **经验教训（供后续 redesign 参考）**：
> 1. "最后一只怪清不掉"对单点改动极不敏感——卡死行为在多个不同改动下稳定维持 70~80%，说明存在尚未定位的深层机制（疑似跨房间寻路/门状态/攻击判定交互）。
> 2. 不要边改边猜：本轮多次把运行噪声（report 写入时序）误读为改善。后续必须固定 build（`--sim-build none`）+ 同 seed 多次重复 + A/B 对照，才能确认收益。
> 3. 诊断先行：先补齐"卡死时完整决策状态可观测性"（best_action / 武器射程 / hunting 态 / 与怪距离时间序列），再针对性修复，避免盲目试错。
> 4. 本设计 §3 的三层方案未经证实有效，不应作为已验证方案直接复用。
> 用户授权：数值/平衡均可调整。这是完整 project（非单点修补），需设计→批准→TDD→实施→重采集基线。

## 一、意图与 why

当前 sim 20 局（seed 4242）基线：`win_rate=0`、`avg_floor=3.9`、`STUCK_RECOVERED=14/20 (70%)`、`boss_kills=[2,0,0]`、死最深 F6。用户要求从"卡在 F3~F5"变成"稳定到 F15 且赢若干局"。

### Goals
- 300 局回归：`STUCK_RECOVERED` 占比显著下降（<20%）、`avg_floor` 明显上升、`win_rate > 0`（赢若干局）。
- 胜利判定口径诚实（见 §7 风险）：到达 F15 且存活才算，不靠超时漏洞。

### Non-goals
- 不改真实游戏（非 sim）的战斗手感与平衡——尽量把改动收敛到 sim 侧或共享数值的可接受范围内。
- 不消除所有卡死（80%→0 不现实），目标是"能通关"，不是"零卡死"。

### Anti-goals（做了就算失败）
- 单点调分数（历史教训：禁站桩曾使胜率 10%→3.5%；分数集合 `sim_ai.cpp:708` 注释"不得随意改动"）。
- 靠放宽胜利判定造假（当前 `victory` 只看 F15+存活，超时也判胜——必须修这个口径）。
- 破坏 sim 确定性（GOLDEN-003 同 seed 必须一致）、破坏存档只读语义。

## 二、现状根因（三份调查结论）

### 2.1 双重瓶颈
| 瓶颈 | 证据 |
|---|---|
| **清不完怪** | 80% STUCK_RECOVERED；门控实验 approach 8.5%→70% 后 stuck 239→237 几乎不变；存活怪满血散布 12~37 格外（`SIM_STUCK_DIAGNOSIS.md:133-160`） |
| **到了深层也打不动** | F15 普通怪 HP×9/ATK×6.5、Boss HP×15/ATK×7（≈9300HP/182ATK，`growth_curve.cpp:10-41`）；sim 玩家裸装 12ATK、每级+2ATK、`skill=0%`、build 全 NONE、avg_relics=0.1；需 ≈290 次命中杀 F15 Boss 而玩家只扛 5~6 下 |

### 2.2 关键机制事实
- **胜利判定漏洞**：`game_scene.cpp:2257` `victory = (floor>=15) && alive`，不检查 Boss 击杀；超时/看门狗结算在 F15 存活会误判胜利（`:2276` 优先于超时分支）。
- **楼梯激活**：必须清光当层所有活怪（`floor_manager.cpp:82-86`）；但 sim 的 descend 动作**不检查站位**（`game_scene.cpp:2850-2852`），故"楼梯不可达"是伪信号，真门槛是清怪。
- **`--sim-build` 是空开关**：`fixed_build_id`（`main.cpp:269`）与 `g_sim_build_type` 全仓无消费者，build 系统没接配装（`调查 B`）。
- **假进展**：`_stuck_progress`（`sim_ai.cpp:1017-1043`）四信号"任一为真即进展"，游荡位移>2格就重置看门狗 → 拖到 120s 才强制结算。
- **站桩死区**：远程 build `ideal_dist≈11~12格`（`sim_ai.cpp:817-819`）导致 9 格内怪全判站桩、approach 被压制；历史单独放开曾致胜率腰斩（`:821-825`）。
- **预算**：120s 卡死预算是**整局累计**（无跨层清零）、600s 帧预算整局、每层 900s、每层 15s 搜刮。

## 三、方案（分三层，协同改）

### 层 1：sim 侧 AI 决策（不改真实游戏）
1. **修复假进展**：`_stuck_progress` 的 `p_move` 改为"与最近怪距离缩短才算进展"，或引入"楼层未清空且长时间无怪掉血"独立计时器。契约测试 `sim_progress_src`。
2. **清怪优先级**：清怪阶段（有存活怪且未清完）临时完全禁用 loot/room/stand 评分，让 approach/attack 胜出；复用 P6 hunt 开关（`sim_ai.cpp:776`）扩展，不动 recovery/dodge/heal。
3. **BFS 震荡修复**：用 `_mem_*` 路径记忆（`sim_ai.cpp:1190-1213`）稳定首步方向，避免每帧重算方向横跳。
4. **站桩死区**：仅对"怪在射程外但 <ideal"的情况给 approach 一个高于 0 的分数（不直接删站桩），需 500 局回归验证。

### 层 2：数值/平衡（用户已授权）
1. **成长曲线**：`growth_curve.cpp:10-41` 敌人 HP/ATK 倍率下调（F15 普通怪 ×9→3~4、Boss ×15→4~5、ATK ×7→2~2.5）。
2. **玩家成长**：`game_scene_combat.cpp:60-63` 每级 ATK +2→+5~8、HP +10→+30~50，使 F15 约 Lv11 时面板能对标。
3. **让 sim 用技能**：查 `skill=0%` 根因（评分竞争/冷却），修 `_evaluate_skill` 使 Boss 战真正放技能。
4. **预算放宽**：`kStuckTotalBudget 120→300~600`（`sim_ai.cpp:78`）、`_sim_wall_frames 36000→108000+`（`game_scene.cpp:756`）。

### 层 3：口径诚实 + 接 build
1. **修胜利判定**：`game_scene.cpp:2257` 改为 `floor>=15 && alive && F15 Boss 已击杀`，排除超时漏洞；或至少把超时结算排除出 VICTORY。
2. **接 build 开关**：把 `fixed_build_id`（`main.cpp:269`）接到实际配装生成，使 `--sim-build` 真正生效（可选，视前两层是否已达标）。

## 四、实施策略（TDD + 切片）

每个切片：先加契约测试（RED）→ 实现（GREEN）→ 构建 → 小样本 sim 验证 → 下一片。

1. **切片 0 — 口径与契约**：修 victory 判定；加"每局楼梯必可达/最后一只怪必可清"契约测试（诊断 `SIM_STUCK_DIAGNOSIS.md:48-50` 要求的 RED→GREEN）。
2. **切片 1 — 清怪 AI**：层 1 的 1/2/3 + 站桩谨慎改，契约测试 `sim_progress_src`/`combat_focus_tracker`。
3. **切片 2 — 数值重配**：层 2 的成长曲线 + 玩家成长 + 技能启用 + 预算。
4. **切片 3 — 验收**：300~500 局回归 + golden 重采集 + build 接线（可选）。

## 五、验证与验收

- **KPI（300 局 seed 多样）**：`STUCK_RECOVERED` 占比 <20%（基线 70%）、`avg_floor` 明显 >3.9、`win_rate>0`（赢若干局）、`boss_kill_counts` 中 F10/F15 非零。
- **确定性**：GOLDEN-001/002/003 必过；有意改玩法则按重采集 SOP（见下）更新基线 + 归因验证（临时回退改动确认旧基线恢复）。
- **无退化**：卡死率下降 + 胜率/avg_floor 不跌出历史带；负回归即回退（P1C6 铁律）。
- **标准闸门**：ctest 全量、fn_length 0、validator 0/0、桌面同步（规范 11）。

### Golden 重采集 SOP（调查 C）
1. 跑 `--sim 4 --sim-seed 4242 --sim-build none`，读 `runs[0..3]` 的 floor/kills/damage/weapon。
2. 替换 `golden_baseline_test.cpp:83-87` 的 base_* 数组。
3. 加 `══ P? 基线更新 (2026-11-23) ══` 归因注释（改了什么/哪几局漂移/量化效果）。
4. 归因验证：临时回退改动重跑 seed 4242，确认旧基线完全恢复（证明非环境漂移）。
5. commit message 按模板写"玩法为什么变"。

## 六、约束与红线

- 改 `sim_ai.cpp` 决策只影响 sim 侧（无 GameplaySystemDirector 调用关系）——已核实；但改共享数值（growth_curve/game_scene_combat）会影响真实游戏，需更广回归。
- 不破坏 sim 存档只读（`SaveManager::g_sim_readonly`/`MetaSystem::g_readonly`）。
- 不新增 gameplay `rng()` 调用或改变调用顺序（P1C8/RNG-002 教训）。
- 函数 ≤40 行、单一职责、语义命名、`#pragma once`、snake_case JSON（CLAUDE.md）。

## 七、风险与诚实评估

- **成功率不确定**：F15 Boss 需 ≈290 次命中、玩家扛 5~6 下，数值需大幅重配才可能赢；"稳定赢若干局"可能需要多轮迭代调参，不是一次设计能保证。
- **历史教训**：多次单点修补被回退；本设计强调协同改 + 500 局回归，仍需实测验证。
- **胜利口径漏洞**必须先修，否则"赢"可能是假的。

## 八、Builder 审查后的决定（用户已拍板 + 实施者决定）

### 用户拍板（3 项）
1. **假进展主导路径 = 独立计时器 + 纯追怪**（不收紧 `p_move`）：新建"楼层未清空且长时间无怪掉血"计时器，超时切纯追怪模式（切模式，不立即结算）。可同时改善卡死率与 avg_floor。
2. **达标门槛 = `win_rate ≥ 5%` 且 `boss_kill_counts` 的 F10/F15 非零**（300 局至少 15 胜，且证明能打到并赢下深层，排除 F15 超时漏洞）。
3. **胜利口径 = 排除超时/看门狗路径**：仅正常 descend 清完 F15 判胜；900s/看门狗结算的 F15 存活改判 TIMEOUT/STUCK。不改存档，golden 基线本就不断言 victory → 不动。

### 实施者决定（builder 审查后）
4. **清怪阶段 = 扩展 P6 tracker，不替换**：`有活怪且未清完` 时禁 loot/room，**保留 recovery/dodge/heal**；不加历史被回退的"禁站桩"（`sim_ai.cpp:821-825`），只给 approach 一个高于 0 的分。
5. **共享数值加 `g_sim_mode` guard**：`growth_curve` / 升级成长改动只在 sim 生效，真实 3D 游戏平衡不动（守 Non-goal）。
6. **快速代理**：`--goto-floor 15` 批准作调参快速代理（需明确其面板写死、无自然装备的口径豁免），最终验收必须全量 sim。
7. **调参主指标 = win_rate**，护栏 = 卡死率不反弹；**切片 1+2 当一个原子变更验证**（避免中间负回归被误退）；golden 基线**最终一次性重采集**。
8. **预算放宽**：120→240s 做带回退闸门的实验（记录 `sim_ai.cpp:76-77` 的 240s 历史负结果），实测更差则砍；`_sim_wall_frames` 暂不动（避免拉长回归）。
9. **build 接线 = 切片 3 必做**（`skill=0%` + build NONE 是核心瓶颈，不做 win_rate 大概率为 0）；但 golden 使用的 `--sim-build none` 路径必须保持原样。

### 留给实施中的取值
- 成长曲线/ATK 成长/预算的具体数值按 300 局实测迭代确定（主指标 win_rate，护栏卡死率）。
